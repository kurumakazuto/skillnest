# skillnest

IT エンジニアが**スキルシート（職務経歴書）を Web 上で作成・管理**できるアプリです。
紙のスキルシートに近い表形式の 1 画面で基本情報と案件履歴を編集でき、文章項目は **AI（Claude）が事実を足さずに読みやすく整えて**くれます。

個人開発 / 学習目的で、Nuxt・Prisma・FastAPI・LLM API を一通り自分で組んでみることを狙いに作りました。

---

## 開発の進め方

Claude Code を使い、**実装しながら分からない箇所をその場でキャッチアップし、書いたコードを小まめにレビューしてもらう**形で進めました。Nuxt のフルスタック構成も Prisma も FastAPI も LLM API も未経験の領域だったので、「なぜこう書くのか」を都度確認しながら進められたのは大きかったです。

ただし、**返ってきた内容をそのまま採用することはしませんでした。** 提案が一般論として正しくても、このアプリの性質や自分で決めたルールに照らすと合わないことが少なくなかったためです。

自分の判断で退けた / 変更した例:

| 場面           | 提案                         | 自分の判断                                                                                             |
| -------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------ |
| 確認ダイアログ | 背景クリックで閉じる         | OK / キャンセルを選ばせるダイアログが勝手に閉じるのはユーザーが戸惑う。閉じないようにした              |
| 案件行の削除   | その場で配列から削除         | スキルシートは頻繁に行を出し入れするものではない。ソフト削除にして誤操作に備えた                       |
| DB 設計        | 既存の多対多設計のまま進める | ユーザーが自由入力する値を全ユーザーで共有する意味がない。非正規化に踏み切った                         |
| 関数名         | `isOutOfRange` のまま        | boolean からオブジェクトを返す実装に変えたので `validateOutOfRange` に改名。処理を変えたら名前も変える |
| 必須項目       | 必須を外す案                 | 案件は空行ができうるので、必須チェックには意味がある。残した                                           |

生成されたコードがそのままでは動かないことも、頼んでいないリファクタが混ざることもあったので、**必ず自分で読んでから取り込む**ようにしていました。結果として「AI に書かせる」のではなく「**AI に相談しながら自分で決める**」進め方に落ち着いています。

## できること

### アカウント

- メールアドレスとパスワードでのアカウント作成・ログイン・ログアウト
- アカウント削除（確認ダイアログ付き。資格・技術・案件などの関連データも連鎖削除）

### 基本情報

氏名 / ふりがな / 性別 / 生年月日（**年齢は誕生日から自動計算**）/ 国籍 / 配偶者の有無 / 最寄駅
保有資格（取得年月 + 資格名を 7 行）/ 経験技術（Enter でタグ追加）/ 得意分野 / 自己PR

### 案件履歴

案件ごとに以下を記録できます。

| 項目     | 内容                                                                                        |
| -------- | ------------------------------------------------------------------------------------------- |
| 期間     | 開始日・終了日。「継続中」にチェックを入れると「現在」表示になる                            |
| 案件情報 | プロジェクト名 / 業務概要                                                                   |
| 規模     | 役割（PG・SE・PL・PM・PMO）/ 開発規模 / 全体規模                                            |
| 環境     | サーバ / OS / DB / FW・MW・ツール / 使用言語                                                |
| 作業工程 | 要件定義・基本設計・詳細設計・実装単体・結合テスト・総合テスト・保守運用の 7 段階をチェック |

- 新しい案件が**一覧の上に来る**逆順表示
- 削除は**その場では消さずグレーアウト**し、保存を押して初めて確定（誤操作しても緑の復元ボタンで戻せる）

### ✨ AIで整える

得意分野・自己PR・業務概要の各欄にボタンがあり、押すと Claude が文章を整えてくれます。

- **書かれていない事実を足さない / 誇張しない**をシステムプロンプトで明示
- 表現・語順・誤字脱字だけを整え、各欄の文字数上限（150 / 300 / 300 字）に収める
- 処理中はローダーを表示してボタンを無効化

### 技術スタック

| 領域         | 使用技術                                                                     |
| ------------ | ---------------------------------------------------------------------------- |
| 画面         | Nuxt 4（SPA / `ssr: false`）、Vue 3、TypeScript、Tailwind CSS v4             |
| バックエンド | Nuxt の Nitro（`server/api/`）                                               |
| DB           | MySQL + Prisma 7（driver adapter 方式 / `@prisma/adapter-mariadb`）          |
| 認証         | argon2id によるパスワードハッシュ + jose の JWT（HS256 / 7日 / Cookie 保存） |
| AI 整形      | FastAPI + Anthropic SDK（Claude）                                            |
| 開発環境     | Prettier / husky / lint-staged                                               |

`server/api/` にすべての DB アクセス・認証・バリデーションを寄せているため、**画面もバックエンドも TypeScript ひとつで、型定義もそのまま共有**できています。FastAPI に切り出したのは AI 整形だけです。

### リクエストの流れ

```
ブラウザ
  │  composables（useFetch / $fetch）
  ▼
Nuxt server/api（Nitro）─── Prisma ──▶ MySQL
  │
  └─ /api/skillSheet/refine ──▶ FastAPI /refine ──▶ Claude API
```

AI 整形だけは FastAPI に切り出し、Nuxt 側はプロキシに徹しています。
**API キーはサーバー側だけが持ち、ブラウザには一切出ません。**

### API 一覧

| メソッド   | パス                             | 内容                               |
| ---------- | -------------------------------- | ---------------------------------- |
| POST       | `/api/auth/signUp`               | アカウント作成（メール重複は 409） |
| POST       | `/api/auth/signIn`               | ログイン（失敗は 401）             |
| DELETE     | `/api/auth/deleteAccount`        | アカウント削除                     |
| GET / POST | `/api/skillSheet/basicInfo`      | 基本情報の取得・保存               |
| GET / POST | `/api/skillSheet/projectHistory` | 案件履歴の取得・保存               |
| POST       | `/api/skillSheet/refine`         | AI 整形（FastAPI へ中継）          |
| POST       | `/refine`（FastAPI）             | Claude を呼んで整形結果を返す      |

### データモデル

```
User ─┬─ Qualification  （資格）
      ├─ Skill          （経験技術）
      └─ Project ─┬─ TechStack （FW・MW・ツール）
                  └─ Language  （使用言語）
```

すべて `onDelete: Cascade`。ユーザーを消せば配下も消えます。

## 大変だったこと

途中で作り直しになったもの、原因の切り分けに時間がかかったものです。

### 1. DB 設計を途中で作り直したこと

当初は資格・経験技術・FW・使用言語を**マスタテーブル + 中間テーブルの多対多**で設計していました。
しかし作り進めるうちに「**ユーザーが自由入力する値なのに、なぜ全ユーザーで共有しているのか**」という根本的な矛盾に気づきます。

マスタ共有だと、表記ゆれ（`MySQL` / `mysql` / `My SQL`）がそのまま `UNIQUE` なマスタに増え続け、誰も参照しなくなった孤児レコードの掃除も必要になり、退会時の削除も複雑になる。「マスタを編集する画面があるならまだしも、そうでないなら共有する意味がない」と判断し、**すべてユーザー / プロジェクト直下に持つ形へ非正規化**しました（`20260627111108_denormalize_master_tables`）。

結果として副次的な効果がいくつもありました。

- 外部キーを `RESTRICT` → `CASCADE` に張り替えられ、**アカウント削除が `user.delete()` 1 行**で済むようになった（マスタ共有のままだと制約違反で消せない）
- 保存処理を「全削除 → 作り直し」に単純化できた。1 ボタンで全体を保存する UI なので、差分検出を書かずに済む
- 取得も `include` 1 段で済むようになった

もちろん「同じスキル名が重複する」「スキル横断の検索ができない」というトレードオフはありますが、これは**自分のスキルシートを作るための個人向けツール**であって横断検索の要件がないので、整合性より書き込みの単純さを取りました。

スキーマだけでなく API・型定義・フロントの処理まで芋づる式に修正が必要で、正直かなり気が重い作業でした。ただ、**なぜ多対多にしていたのかを自分で説明できないまま進めていた**ことが問題の本質だったので、やり直して正解だったと思っています。

### 2. 案件履歴テーブルの行管理

一覧まわりは想定以上に詰まりました。

- 追加ボタンで行を増やすと、**入力した内容が新しい行にもそのまま出る** → 同じオブジェクトの参照を使い回していたのが原因で、ディープコピーが必要だった
- `v-for` の `key` に配列のインデックスを使うと、行の削除で表示がズレる
- データは末尾に追加したいが、画面では新しい案件を上に出したい（表示だけ逆順にする）
- 途中の行を削除すると No. が `1, 3` のように飛ぶため、**振り直しの処理が必要になる**

最後の問題は、そもそも「その場で消す」のをやめることで解決しました。削除ボタンは行をグレーアウトするだけにして、**保存を押して初めて DB に反映される**方式にしたのです。これで番号の振り直し処理ごと不要になり、しかも誤操作しても復元ボタンで戻せるようになりました。スキルシートは頻繁に行を出し入れするものではないので、UX 上も問題ないと判断しています。

問題を正面から解くのではなく、**そもそも問題が起きない形に変える**ほうが早いことがある、というのが一番の学びでした。

### 3. エラー表示の設計

最初は「各入力項目にエラーフラグを持たせる」案を考えましたが、それだと `techStacks: string[]` のような素直な型を**全部オブジェクトに作り替える**必要があり、API の送受信の形まで変わってしまいます。

そこで**エラーはデータに埋め込まず、別の入れ物に持つ**方針に変更しました。

```ts
interface DisplayError {
  message: string
  field?: 'title' | 'summary' | 'techStacks' | ... // 入力欄を赤くする時だけ
  projectIndex?: number                            // 何番目の案件か
}
```

これでデータモデルは汚れず、バリデーションをやり直すときも配列を作り直すだけで済みます。`field` を文字列リテラルのユニオンにしてあるので、項目名のタイプミスはコンパイルエラーで弾かれます。

同じメッセージが何件も並ぶ問題は、ダイアログ側で `Set` を使って重複排除しました。ただし `errors` 配列自体は `projectIndex` 付きで全件持っているので、**メッセージは 1 行に集約しつつ、赤くなる入力欄は該当箇所すべて**という挙動になっています。

`DisplayError` という名前にしたのは、入力エラーだけでなく**サーバーから返ったエラーの表示にも同じダイアログを使い回す**つもりだったからです。実際いまはその 1 つで全部まかなえています。

### 4. 保存と再取得の実行順

保存後に最新データを取り直したいのに、**DB の更新が終わる前に取得が走ってしまう**ことがありました。デベロッパーツールで見ると取得 API がそもそも発火していないケースもあり、原因の切り分けに時間がかかりました。

最終的に、`useFetch` と `$fetch` を役割で使い分ける形に整理しました。

- **取得は `useFetch`** を `immediate: false` で用意し、保存完了後に明示的に `refresh()` を呼ぶ
- **保存は `$fetch`**。単発で 1 回送るだけの操作なので、キャッシュも再発火もいらない

初回表示時の二重発火もこの整理で解消しました。

### 5. 初めての FastAPI と LLM API

Python も FastAPI も未経験だったため、`main.py` と router を分ける意味、`include_router` が何をしているのか、`uvicorn main:app --reload` が何を起動しているのかを、一つずつ確認しながら進めました。

LLM API 側も、**API キーが課金と紐づくこと自体を知らないところ**からのスタートで、キーの発行・クレジットの購入・環境変数での受け渡しまで含めて調べる必要がありました。

## 工夫したこと

こちらは手戻りではなく、最初から意図してそう設計した部分です。

### バリデーションをフロントとサーバーの両方に置いた

同じルールを二層で持たせていますが、**返し方をわざと変えて**います。

- サーバー（`server/utils/validation.ts`）は違反を見つけたら即 `createError` で 400 を投げて止める。改ざんリクエストへの防壁なので、全件を数え上げる必要がない
- クライアント（`utils/validation.ts`）は `{ hasError, errorMessage }` を返すだけ。**全エラーをまとめて 1 つのダイアログに出したい**ので、途中で例外を投げてはいけない

文字数の上限は、フロント・サーバー・AI 整形のプロンプトの 3 箇所で同じ値を守るようにしています。

### ユーザー ID をリクエストから受け取らない

保護された API はすべて `getUserIdFromCookie()` を先頭で呼び、**ユーザー ID を必ず JWT から導出**しています。クライアントから `userId` を受け取る口をどこにも作っていないため、他人の ID を送って他人のデータを読む、という事故が構造的に起きません。

ログイン失敗時も、ユーザーが存在しない場合とパスワードが違う場合で**同じメッセージ・同じ 401** を返し、メールアドレスの存在を推測されないようにしています。

### API キーをブラウザに出さない構成

AI 整形は「ブラウザ → Nuxt の `server/api` → FastAPI → Claude」と経由させ、キーを持つのはサーバーだけにしました。FastAPI の URL も `runtimeConfig` のサーバー専用キーに置いているので、クライアントのバンドルには出ません。フロントは自前の `/api/skillSheet/refine` を叩くだけです。

### 画面専用の項目を API の型に混ぜない

案件一覧では「画面上の通し番号」と「継続中チェック」が必要ですが、これらは DB にも API にも存在しません。そこで交差型で画面側にだけ足しています。

```ts
type ProjectHistoryWithNumber = ProjectHistory['projectHistoryList'][number] & {
  projectHistoryNumber: number
  isOngoing: boolean
}
```

取得時は `endDate === null` から `isOngoing` を復元し、送信時は分割代入で剥がす。**API 型 → 画面型 → API 型の変換境界がはっきり**し、API の契約型は汚れません。

その API 契約型（`types/api/**`）はサーバーのハンドラの戻り値型としても使っているので、レスポンスの形を変えるとサーバー側がコンパイルエラーになります。フロントとバックの型ズレをビルド時に検出できるのは、Nuxt をフルスタックで使う一番の利点だと感じました。

### 紙のスキルシートに寄せた UI

実務で使われる Excel 帳票の見た目に近づけるため、固定幅の罫線グリッド、スクロールしてもヘッダーが残る `sticky` 指定、作業工程の**縦書きラベル**（`writing-mode: vertical-rl`）を実装しました。フォントも Web フォントをやめて MS Pゴシック系に変えています。

年齢の自動計算、「継続中」チェックで終了日欄が消える挙動、資格欄を常に 7 行表示するなど、**紙の様式に寄せつつ入力の手間を減らす**ことを意識しました。

### 通知の種類で見せ方を変える

- **エラー**は操作を止めて気づかせたいのでモーダル（`DisplayErrorDialog`）
- **成功**は流れを止めたくないので 3 秒で消えるトースト（`Toast`）
- **取り返しのつかない操作**（アカウント削除）は確認ダイアログ（`ConfirmDialog`）

トーストは連打してもタイマーが多重にならないよう、再表示のたびに `clearTimeout` してから張り直しています。

### 認証を自作した

学習目的で、パスワードハッシュ（argon2id）・JWT の発行と検証・Cookie 保存・ルートガードを自分で実装しました。クライアント側はトークンの有無だけを見て画面遷移を制御し、**正当性の検証は必ずサーバー側で行う**二段構えにしています。
（実運用を見据えるなら `nuxt-auth-utils` などに寄せるべき、というのは認識しています）

## 今後の課題

学習目的で割り切った箇所や、把握しているが未対応の点です。

- **認証**: 学習のため自作したが、実運用を見据えるなら `nuxt-auth-utils` などに寄せたい。トークンもサーバー側で `HttpOnly` Cookie として発行すべき（現在はレスポンスで返してクライアントが保存している）
- **保存方式**: 毎回「全削除 → 作り直し」なので、資格・技術・案件の id が保存のたびに変わる。差分更新にしたい
- **案件の途中挿入**: 現在は末尾にのみ追加できる
- スキルシートの PDF / Excel 出力
- 経験技術の入力をコンボボックス（入力可能なプルダウン）に
- `backend/` の `requirements.txt` を用意する
- デプロイ
